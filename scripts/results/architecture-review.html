🔍 KTD.jl Architecture Review

src/visualization.jl · 1,850 lines · 1 monolithic function · 15 captured variables in _rerun! closure

Executive Summary

build_dashboard() is a shallow module by the codebase-design vocabulary: its interface takes layout=:v1|:v2 but its implementation is a single 1,850-line function where panels, controls, scenarios, and the simulation runner are all defined inline as closures capturing 15+ variables.

The deletion test: deleting any single piece (the _rerun! closure, a panel, the controls) would require rewriting N callers that depend on the captured variables. This is the definition of low locality.

Vocabulary: module · interface · depth · seam · adapter · leverage · locality — per codebase-design skill

1. Extract _rerun! from build_dashboard

STRONG
📁 Files
visualization.jl:850-1070
🔗 Captures
15 outer variables
📏 Size
~220 lines

Problem

The _rerun! closure captures sys, p, u_settled, wind_fn, speed_slider, payout_slider, sim_frames_obs, ext_frames_obs, frame_slider, times_ref, and 5+ control booleans from the outer scope. It's coupled to v1's grid positions (controls at fig[1,1], HUD at fig[1,3]). V2 can't reuse it because v2's cockpit strip occupies fig[1,1:4].

Solution

Extract as build_rerun!(sys, p, u0, wind_fn, lift_device, obs_nt) → closure where obs_nt is a NamedTuple of observables the runner reads/writes. Both v1 and v2 pass their own observables — the runner logic is identical.

Benefits

  • Leverage: One runner serves two layouts — add a third layout with zero changes
  • Locality: Bug in simulation stepping? Fix in one place, both layouts fixed
  • Testability: build_rerun! returns a closure — call it with mock observables, verify frames produced

2. Extract Panel Functions

STRONG
📁 Files
visualization.jl (various)
+ prototype scripts
📦 Panels
6 panel types
🔄 Interface
grid_cell + data_obs

Problem

Panel visuals are defined inline in build_dashboard. They can't be swapped between layouts or cells. The prototype panels (torque chain, ring health, rotor gauges) exist as standalone CairoMakie scripts but aren't callable from the GLMakie dashboard.

Solution

Each panel becomes a function: torque_chain!(grid_cell, data_obs::Observable{ExtendedSimFrame}). Creates its own axes/plots, reads from the observable. Doesn't know about frame_obs or ext_frames_obs — just receives data.

After: panels as deep modules

Benefits

  • Leverage: One panel implementation, N cells can display it
  • Locality: Fix ring health bar colour logic in one function, all layouts see it
  • Testability: Call ring_health!(cell, obs), push data to obs, verify bar colours

3. Configurable Cell Slots

WORTH EXPLORING
📁 visualization.jl + new panel_registry module

Problem

After extracting panels, the grid still has fixed assignments. A structural analysis workflow wants ring health bars + torque chain. A power optimization workflow wants rotor gauges + tension chain. Currently you'd need different dashboard functions for each.

Solution

configurable_cell!(grid_cell, panel_registry, selector_obs) — a cell stores [panel_fn1, panel_fn2, ...] and calls the one selected by selector_obs[]. Each cell gets an independent dropdown.

Benefits

Same dashboard shell, different workflows. Investor demo gets rotor gauges + 3D viewport. Engineering review gets ring health + torque chain. No layout duplication.

🎯 Top Recommendation

Start with Candidate 1 (extract _rerun!) + Candidate 2 (extract panels) together.

These are a natural pair: _rerun! produces ExtendedSimFrames, panels consume them. Extracting both creates a clean seam between data production and visualisation. After both are extracted, Candidate 3 (configurable cells) is a thin layer on top — add a dropdown per cell that swaps which panel function it calls.

Estimated: ~300 lines changed, ~150 new. V1 dashboard test passes unchanged. V2 layout becomes a thin shell composing the extracted components.
