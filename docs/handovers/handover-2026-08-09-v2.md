## 1. What We Found

### Drag double-count bug — FIXED

`parasitic_drag_power` (objective_v6.jl) was computing expansion blade profile
drag and subtracting it from the power balance. But `expansion_rotor_forces`
(expansion_rotor.jl) already computes net torque as `τ_lift - τ_drag` — drag
was being subtracted TWICE.

**Fix:** Removed the expansion blade drag section (lines 337-368 of
objective_v6.jl). Expansion rotor drag is already handled correctly by
`expansion_rotor_forces` in both the static solver and the ODE.

**Effect on seed genome:**
| | Before fix | After fix |
|---|---|---|
| ω_eq (static solver) | 42.2 rpm | **50.3 rpm** |
| P_gen | 41.1 kW | **69.8 kW** |
| P_par | 111.1 kW | **15.8 kW** |
| Expansion blade drag | 101.4 kW (phantom) | 0.0 kW (correct) |

Net power (P_gen - P_par) went from negative to **54 kW** — above the 50 kW
target. The fix is correct and material.

### Ring mass corruption — NOT FIXED, NOT FROM TODAY

`build_system_from_v10` produces hub ring mass ~386 kg but intermediate TRPT
rings = 1.0e30 kg. This means FoS values (37-855) are measuring a free-lunch
artefact: impossibly stiff rings with near-zero mass penalty.

This is a pre-existing bug in the build path — `sys.ring_Do_top[]` and
`sys.ring_toverD[]` are not populated for intermediate rings. The fix needs
to happen in `build_kite_turbine_system` or `build_system_from_v10`.

### Power-to-weight of best design

Using geometry-based mass estimate (ring mass is corrupted, so direct
decode gives garbage):

- 8 lines × 10 rings, Do_top=0.28m, t/D=0.15
- Estimated ring mass: ~3,200 kg
- P/W ≈ 1.9 W/N (0.018 kW/kg)

This is the over-engineered penalty of FoS=142. A design optimized for
FoS≈3.5 would use thinner tubes, cutting mass by 10-40×.

## 3. What Needs Verification on Laptop Side

### Priority 1: Ring mass bug
Verify that `sys.ring_Do_top[]` and `sys.ring_toverD[]` are set for ALL ring
indices (1..sys.n_ring) after `build_system_from_v10`. Currently only the hub
ring gets a valid mass. Print `node.mass` for all RingNode instances — any
mass > 1e6 = still broken.

**Implication:** Until this is fixed, all FoS values from any campaign are
measuring a free-lunch artefact. The 5 "feasible" designs above may not be
feasible under honest ring sizing. The DE objective and the FoS gate are
both affected.

### Priority 2: ODE speed
The ODE runs at 0.15-0.22 sim-s/wall-s. Each warmstart eval takes 25-30 min.
This is inherent — `compute_rope_forces!` allocates ~7,300 vectors per step.
The per-step allocation fixes saved ~7%. A pre-allocated workspace buffer
would eliminate the remaining allocations but requires a more invasive refactor
of the inner loop.

### Priority 3: FoS optimisation target
Current objective drives toward raw power with no mass penalty, so the DE
finds the stiffest possible rings = highest FoS = heaviest design. Switching
to target FoS≈3.5 (penalize distance from target in both directions) would
steer designs toward the efficient frontier.
