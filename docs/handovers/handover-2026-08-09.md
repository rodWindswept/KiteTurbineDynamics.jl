## 1. What We Found

### Double-counted expansion blade drag (CRITICAL)

`src/objective_v6.jl:parasitic_drag_power()` contained a section (lines 337–368) that computed expansion blade profile drag and subtracted it from the power balance. However, `expansion_rotor_forces()` (in `src/expansion_rotor.jl`) already computes net torque as `tau_net = tau_lift - tau_drag`, where `tau_drag` includes profile + induced + post-stall drag. The static solver uses `tau_net * omega` as `P_exp_net`.

**Effect:** Expansion blade drag was subtracted TWICE from the power balance:
- Once correctly inside `expansion_rotor_forces()` (via `tau_net`)
- Once incorrectly in `parasitic_drag_power()` (as `P_exp_blade_total`)

**Before fix:** P_par = 111 kW (101 kW phantom expansion drag + 8.5 kW tether + 1.3 kW beam). Static solver found ω_eq = 42 rpm, P_gen = 41 kW.

**After fix:** P_par = 16 kW (8.5 kW tether + 1.3 kW beam + 0 kW expansion). Static solver finds ω_eq = 50 rpm, P_gen = 70 kW. Net = 54 kW — above the 50 kW target.

### n_rings gate too restrictive

The gate required n_rings ≥ 5 intermediate rings. Rod directed relaxation to ≥1, allowing the simplest TRPT: ground ring + 1 intermediate + hub ring = 3 total rings. Hub ring carries the topmost expansion rotor.

### ODE allocation hot spots

`rope_forces.jl:get_subsegment_tension()` recomputed `diff_pos`, `current_len`, and `dir` that the caller (`compute_rope_forces!`) had already computed. Combined with `.+=` broadcast temporaries and non-view velocity slices, each of ~600 subsegments allocated ~16 short vectors per ODE step. At 4e-5 dt and 150s sim = 3.75M steps, that's billions of allocations.

## 2. Changes Made

### `src/objective_v6.jl` — Remove double-counted expansion blade drag
- Replaced the expansion blade drag computation block (lines 337–368) with `P_exp_blade_total = 0.0`
- Added comment explaining why: drag is already inside `expansion_rotor_forces().tau_net`
- Tether drag (curvature factor 0.5) and beam drag unchanged

### `src/objective_v11.jl` — n_rings gate
- Warmstart path (line ~357): `if n_rings < 5` → `if n_rings < 1`
- Cold path (line ~196): same change
- Comment updated with rationale

### `src/rope_forces.jl` — Allocation fixes
- `get_subsegment_tension()` signature changed: accepts pre-computed `diff_pos`, `current_len`, `dir` instead of `pa`, `pb`
- Three call sites updated (`compute_rope_forces!`, `get_max_rope_tension`, `get_segment_tension`)
- `end_vel()` returns `@view` instead of copy
- `.+=` and `.-=` broadcasts replaced with explicit `for k in 1:3` loops
- `0.5 .* drag` pre-computed as `half_drag` before the per-endpoint loops
- ~7% allocation reduction per ODE step

### `scripts/run_feasibility_phase_a.jl` — Campaign fixes
- **OOM fix:** `save_row()` now appends to in-memory `ROWS_BUFFER` under lock; `flush_csv()` writes all buffered rows at generation boundaries
- **GC:** `GC.gc()` called between generations (after flush)
- **Decay checkpoint:** `evaluate_genome()` runs warmstart at 30s first. If P < 1 kW, returns "decay_30s" tier without running full 120s
- **Threading:** `existing_hashes` cached once before `@threads` block (was being re-read inside the loop)
- **Campaign size:** POP=6, MAX_GENS=4 (was 8/6)
- **Output:** `scripts/results/recampaign/feasibility_phase_a_v3.csv`

## 5. Open Issues

- **ODE performance:** 25–30 min per warmstart eval. `compute_rope_forces!` still allocates heavily via `attachment_point()`. A workspace-buffer refactor would help.
- **Stationarity:** No design ever reaches stationary=true. The relax sensitivity data from 2026-08-05 showed all 5 test genomes decaying toward zero power by 120s. Whether this is a physics problem (designs can't sustain power) or a numerical problem (warmstart initializes at wrong ω) is unresolved.
- **Curvature factor:** The tether drag curvature factor (0.5) was not recalibrated because expansion blade drag dominated. After the fix, tether drag (8.5 kW) is the main parasitic term and could benefit from ODE-calibrated tuning.
- **Campaign OOM:** Still OOMs after ~30 evals. The 12-hour timeout catches it with partial results. For longer campaigns, either reduce thread count or add explicit GC pressure relief during ODE.
